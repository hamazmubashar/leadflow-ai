# ADR 0003: M2 local SQLite persistence and lead REST API

- Status: Accepted
- Date: 2026-10-14

## Context

M2 adds storage and an authenticated HTTP API for leads on top of M0 (service foundation) and M1 (pure-Python validation).

**Constraints:**
- Local only: no paid services or external APIs.
- Python 3.12.
- Reuse M1 validation and M0 bearer authentication.
- Duplicate email or phone identities are rejected, never merged.
- No dashboard, scoring, LLM, or message sending.

The project version is now `0.2.0`.

## Decisions

### 1. Storage stack
- **Database and tools:** SQLite through **synchronous** SQLAlchemy 2.1, with Alembic 1.20 for every schema change. Alembic also brings in Mako and MarkupSafe.
  - Async was rejected: it would need `aiosqlite` and buys nothing for a local single-file database.
  - FastAPI runs the sync endpoints in its thread pool.
- **Configuration:**
  - `DatabaseSettings` holds `LEADFLOW_DATABASE_URL` (default `sqlite:///./leadflow.db`) and **contains no secrets**, so Alembic can load it without the operator token. `Settings` (the API) extends it with the token.
  - URLs must be local SQLite *files*. Other drivers, in-memory databases, hosts, credentials, and query parameters are rejected.
  - `hide_input_in_errors=True` keeps configured values (the URL, the token) out of validation error messages. That also fixed an M0 issue where a too-short token appeared in the startup error.
- **Engine and connections:** created by `create_db_engine(DatabaseSettings)`. Every connection gets:
  - `PRAGMA journal_mode=WAL`, so readers aren't blocked by the writer.
  - `PRAGMA busy_timeout=5000`.
  - `PRAGMA foreign_keys=ON`.
  - `check_same_thread=False`, which is safe because each request uses its own session.
  - `hide_parameters=True`, so SQL parameter values (names, emails, phones) never appear in database error messages.
- **Lazy creation:** the app builds a `Database` holder that creates the engine on first use, thread-safely, and disposes it at shutdown. Building the app and serving `/health` never open or create the database file.

### 2. Schema (migration `0001_create_leads`)
| Column | Type | Constraints |
|---|---|---|
| `id` | `VARCHAR(36)` | primary key, UUID4 string generated by the server |
| `full_name` | `VARCHAR(100)` | NOT NULL |
| `email` | `VARCHAR(254)` | nullable, UNIQUE, CHECK lowercase |
| `phone` | `VARCHAR(16)` | nullable, UNIQUE (E.164) |
| `company` | `VARCHAR(120)` | nullable |
| `source` | `VARCHAR(20)` | NOT NULL, CHECK in the five `LeadSource` values |
| `notes` | `VARCHAR(1000)` | nullable |
| `created_at` | `DATETIME` | NOT NULL, UTC |

- **Table rule:** `CHECK (email IS NOT NULL OR phone IS NOT NULL)`.
- **Constraint names** are fixed by a naming convention: `pk_leads`, `uq_leads_email`, `uq_leads_phone`, `ck_leads_contact_required`, `ck_leads_source_allowed`, `ck_leads_email_lowercase`.
- **Identity:** SQLite's UNIQUE allows multiple NULLs. M1 already stores normalized values, so the two UNIQUE constraints enforce exactly M1's `identity_keys()`.
- **Lengths:** SQLite doesn't enforce `VARCHAR` lengths. M1 validation enforces them, and the CHECK constraints protect against direct SQL writes.
- **Timestamps:** a `UTCDateTime` column type stores UTC without a timezone suffix and returns timezone-aware UTC values. It **rejects datetimes with no timezone**. The API returns times in ISO 8601 with a `Z` suffix.

### 3. Migrations
- **Alembic is the only thing that creates or changes the schema.** The app never calls `create_all`.
- **`0001` was written and reviewed by hand.** Migration files don't import application code, so each one stays a fixed snapshot.
- **Configuration:**
  - `alembic.ini` sets no URL. `env.py` reads it through `DatabaseSettings`, so it gets the same validation and needs no token.
  - `render_as_batch=True` lets future migrations change SQLite tables.
  - `alembic upgrade head --sql` (generate SQL without connecting) is supported.
- **Workflow:** `uv run alembic upgrade head` before first use and after upgrades. `downgrade base` drops all data.
- **Tests check:**
  - Upgrade, downgrade and upgrade again.
  - No differences between the ORM models and the migrated schema.
  - CHECK constraints compared explicitly, because Alembic's comparison skips them.
  - Every constraint enforced on direct SQL inserts.
  - Migrations without a token, and with no ini file.
- **Coverage** is measured by directory (`src/leadflow_ai`), so Alembic's `env.py` and the revision files are included. Alembic loads them under made-up module names that package-based coverage silently skipped.

### 4. Service layer and transactions
- **Functions:** `create_lead`, `get_lead` and `list_leads`, in `services/leads.py`.
- **`create_lead`:**
  - Runs M1's `validate_lead()` first, so invalid input never touches the database.
  - Then looks for existing rows with the same email or phone, inserts, and **commits**.
- **Who commits:** only the service commits. The per-request `session_scope` never commits; it rolls back on any exception and always closes. Sessions keep committed objects readable after commit (`expire_on_commit=False`).
- **Duplicates:**
  - **The UNIQUE constraints decide.** The lookup before inserting only makes the error message precise.
  - If a simultaneous insert slips past the lookup, the commit fails on the constraint. The service rolls back, looks up again, and raises `DuplicateLeadError`, without chaining the original database error, because it contains SQL. Any other integrity error is re-raised.
  - Nothing is merged, partially written or updated.
  - `DuplicateLeadError` carries `(field, lead_id)` pairs only, never contact values.
  - A deterministic test holds 4 threads at a barrier until all have passed the lookup, then lets them insert at once. Exactly one succeeds, and the losers fail at commit.
- **`get_lead`:** accepts only canonical lowercase UUID strings; anything else is "not found".
- **`list_leads`:** newest first, with ties broken by `id` so pages are stable. `limit` is 1–100 (default 50). `offset` is 0 to 2^63−1; larger values overflow SQLite's driver.

### 5. HTTP API
- **Endpoints:**
  - `POST /api/v1/leads` returns 201 with a `Location` header.
  - `GET /api/v1/leads/{id}` returns the lead or 404.
  - `GET /api/v1/leads?limit=&offset=` returns `{items, limit, offset}`.
- **Authentication:** every lead route requires M0's operator bearer token, as a router-level dependency. A test checks that every `/api` operation in the OpenAPI schema is a leads-router route with that dependency.
- **Request body:**
  - The body is read by an authenticated dependency, not a FastAPI body parameter. FastAPI parses declared bodies *before* running dependencies, which would have let unauthenticated clients get 422s.
  - The body must be one JSON object. Duplicate keys, very deep nesting, invalid UTF-8 and non-objects are rejected.
  - **Content-Type:** `POST` requires `application/json`, matched case-insensitively with parameters such as `charset` allowed. Anything else, or no header, gets **415** `request.unsupported_media_type`.
  - **Size limit:** an ASGI middleware rejects bodies over **16 KiB** with **413** `request.too_large` before any parsing, whether or not a `Content-Length` header was sent (chunked uploads included).
  - **Order of checks:** 413 → 401 → 415 → 422.
- **Errors:** responses never repeat submitted values, raw SQL or file paths.

  | Case | Response |
  |---|---|
  | M1 validation | 422 `lead.invalid` |
  | Body isn't one JSON object | 422 `request.invalid_body` |
  | Bad query values (FastAPI's default 422 is replaced, since it echoes input) | 422 `request.invalid` |
  | Duplicate | 409 `lead.duplicate`, with field names and existing ids |
  | Unknown lead | 404 `lead.not_found` |
  | Write lock held past the timeout (`SQLITE_BUSY`) | 503 `database.busy` with `Retry-After: 1`; no automatic retry |
  | Missing table | 503 `database.not_migrated` |
  | Can't open the file (`SQLITE_CANTOPEN`) | 503 `database.unavailable`, with no path |
  | Any other database error | plain 500 |

- **No trailing-slash redirects** (`redirect_slashes=False`). Starlette's redirects copied the requested path and query string into the `Location` header, even for unauthenticated requests. Trailing slashes now return 404.
- **OpenAPI** (`/docs`, `/openapi.json`) stays public. It contains no lead data.

## Known limitations

- **One writer at a time.** A write waits up to 5 s for the lock and then returns 503, tying up a worker thread meanwhile.
- **Migrations aren't transactional on SQLite.** Alembic assumes non-transactional DDL there. `0001` is a single atomic `CREATE TABLE`; a future migration with several steps would need explicit transaction handling.
- **The first lead request against a missing file creates it.** It creates an empty database plus its `-wal` and `-shm` files, then returns `database.not_migrated`. Running the migration fixes it without a restart.
- **`/health` doesn't check the database.**
- **The app doesn't log its own 503s.** uvicorn's access log records the status.
- **Access logs record paths and query strings.** The API never needs personal data in URLs, but clients must not add it.
- **Error shapes differ:**
  - 401 keeps M0's plain string `detail`.
  - Starlette's 404 for unknown paths and the plain-text 500 have no `code`.
- **No `Cache-Control: no-store`** on responses containing personal data (deferred).
- **No update, delete, search, rate limiting, or backups.** One shared operator token, with no per-user access control or audit log.
- **Duplicate detection is exact.** It compares normalized email and phone only, with no fuzzy or name matching, as in M1.

## Consequences

The service can be run, migrated and used entirely on one machine, and the behavior is fully tested: 519 tests, 100% line and branch coverage including migrations, run with the network blocked. Moving to a server database or async I/O would need new decisions about connection settings, error classification (the SQLite error names used above) and migration transactions.
